# Выкладка сайта SC Trade

Сайт — это папка готовых файлов (`site/dist`), которую отдаёт веб-сервер Caddy на своём сервере (VPS).
Здесь: какой сервер взять, как направить на него домен, как войти по ключу, как собрать сайт, выложить его и
проверить. Команды для Windows набираются в PowerShell в папке проекта.

## 1. Какой сервер взять

- VPS (облачный сервер) с Ubuntu 24.04 LTS.
- 1 vCPU, 1–2 ГБ памяти, диск от 20 ГБ.
- Свой публичный адрес IPv4. IPv6 — если хостер даёт, не обязательно.

Сайт лёгкий: страницы, картинки, установщик около 5 МБ и, если будет, фоновый ролик до 12 МБ.

## 2. Направить домен на сервер

В панели регистратора домена `sc-trade.space`, в записях DNS:

- запись `A` для `sc-trade.space` — адрес IPv4 сервера;
- запись `AAAA` для `sc-trade.space` — адрес IPv6 сервера, если он есть.

Проверка (может заработать не сразу, до нескольких часов):

```
nslookup sc-trade.space
```

В ответе должен быть адрес сервера. Сертификат HTTPS Caddy получит сам, когда домен уже показывает на сервер;
до этого сайт по HTTPS не откроется.

Адрес с `www.` не настроен. Если он нужен: добавь такую же запись для `www.sc-trade.space` и убери `#` у блока
в конце `site/deploy/Caddyfile.template` (там написано, у каких строк).

## 3. SSH-ключ и вход по нему

Выкладка входит на сервер только по ключу. Пароль нигде не спрашивается и нигде не хранится.

1. Сделай ключ (один раз):

   ```
   ssh-keygen -t ed25519 -C "sc-trade"
   ```

   Ключ ляжет в `C:\Users\<ты>\.ssh\id_ed25519`, его открытая половина — рядом, в `id_ed25519.pub`.
   На вопрос про парольную фразу можно ответить пустой строкой. Если задашь фразу, перед выкладкой ключ надо
   добавить в агент (`ssh-add`), иначе выкладка не войдёт: она ничего не спрашивает.

2. Когда создаёшь сервер, хостер просит открытый ключ: вставь туда содержимое `id_ed25519.pub`. Это твой вход на
   сервер администратором. Он нужен для настройки сервера (раздел 4), выкладка им не пользуется. Если хостер ключ
   не спросил и дал только пароль, ключ кладётся на сервер одной командой — она в шаге 4.3.

3. Выкладка входит отдельным пользователем, не администратором. В примере он называется `deploy` (поле `user` в
   `deploy.local.json`), и писать ему можно только в папку сайта. Ключ для выкладки должен лежать у этого
   пользователя, а не у `root`: пользователя заводит настройка сервера (раздел 4) и даёт ему те же открытые
   ключи, с которыми входишь ты.

4. После настройки войди один раз руками этим пользователем:

   ```
   ssh deploy@АДРЕС
   ```

   Первый вход спросит, доверять ли серверу (покажет его отпечаток): ответь `yes`. Пароль спросить не должен.
   Этот вход нужен обязательно: выкладка на вопрос про отпечаток ответить не может и до первого ручного входа
   завершится ошибкой.

## 4. Настройка сервера

Сервер настраивает скрипт `setup.sh`. Запускаешь его ты сам, на сервере, под администратором. Он ставит веб-сервер
Caddy, заводит пользователя `deploy` с твоим ключом и папку сайта, ставит службу обратной связи (она принимает
форму сайта и показывает сообщения на странице автора `/admin/`), включает брандмауэр.

Важно знать заранее: **этот скрипт до тебя никто не запускал**. Он написан и вычитан, его части проверены
тестами, но настоящего сервера он не видел. Поэтому сначала проверь две вещи на сервере (шаг 4.3), посмотри, что
скрипт собирается делать (шаг 4.4), и держи открытым второе окно с входом на сервер, пока не пройдёшь проверку
(шаг 4.6).

В командах ниже `АДМИН` — тот, под кем ты входишь на сервер (`root` или имя, которое дал хостер), `АДРЕС` — адрес
сервера.

### 4.1. Собрать папку для сервера

На своём компьютере, в папке проекта:

```
npm run site:build -- --no-installer
```

(или с установщиком, как в разделе 6: папка для сервера получается одна и та же). Появится `site/dist-deploy`:

- `setup.sh` — скрипт настройки;
- `Caddyfile` — настройка веб-сервера;
- `sc-trade-site.service` — описание службы для systemd;
- `logrotate.conf` — правило, которое хранит журнал ошибок веб-сервера не дольше 30 дней;
- `site.conf` — домен, папка сайта и порт службы (из `site/site.config.json`);
- `server/` — сама служба со всем, что ей нужно для работы. На сервере для неё ничего не скачивается.

Паролей, ключей и других секретов в этой папке нет: настройки службы и хеш пароля создаются уже на сервере.

Если сборка остановилась со словами `the service of the site is not installed`, выполни
`npm run site:server:install` и собери ещё раз.

### 4.2. Отправить папку на сервер

Одной командой, в домашнюю папку администратора:

```
scp -r site\dist-deploy АДМИН@АДРЕС:
```

На сервере появится папка `dist-deploy`. Если она там уже лежит с прошлого раза, сначала убери старую, иначе в
ней останутся лишние файлы:

```
ssh АДМИН@АДРЕС "rm -rf dist-deploy"
```

Выкладка сайта (`npm run site:deploy`) эту папку не трогает и на сервер её не отправляет.

### 4.3. Перед запуском: порт SSH и свой ключ

Две вещи скрипт должен узнать о сервере верно. Ошибка в любой из них может стоить тебе входа на сервер, поэтому
проверь обе сам, до запуска.

**Порт SSH.** Скрипт включает брандмауэр и оставляет открытым порт, через который ты входишь на сервер. Порт он
спрашивает у самой системы и ничего не предполагает. Зайди на сервер и посмотри, что она отвечает:

```
ssh АДМИН@АДРЕС
sudo sshd -T | grep -i '^port'
echo $SSH_CONNECTION
```

Первая команда печатает `port 22`. Вторая печатает четыре значения, последнее из них — порт твоего входа: тоже
`22`. Если так — запускай скрипт, как написано в шагах 4.4 и 4.5.

Если хотя бы одна показала другой порт (некоторые хостеры переносят SSH на свой), запускай скрипт так, чтобы он
узнал порт твоего входа. Обычный `sudo` этот порт от него скрывает:

```
sudo --preserve-env=SSH_CONNECTION bash setup.sh
```

Пробный прогон из шага 4.4 запускай так же, с `--dry-run` в конце строки.

Перед тем как включить брандмауэр, скрипт печатает строку `SSH stays open on: …` — порты, которые он оставит
открытыми. Твой порт должен быть среди них. Если система не назвала ни одного порта, скрипт брандмауэр не трогает
вовсе, говорит об этом и делает всё остальное.

**Свой ключ.** Пользователю `deploy` скрипт даёт те же открытые ключи, с которыми входишь ты сам: он берёт их из
списка ключей администратора на сервере. Если хостер принял твой открытый ключ, когда ты создавал сервер (раздел 3,
шаг 2), ключ уже на месте и делать ничего не надо.

Если хостер дал только пароль администратора, а ключ не спросил, положи ключ на сервер сам. На своём компьютере, в
PowerShell, одной строкой:

```
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | ssh АДМИН@АДРЕС "mkdir -p ~/.ssh && chmod 700 ~/.ssh && tr -d '\r' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Команда спросит пароль администратора — в последний раз. Проверь: открой новое окно и набери `ssh АДМИН@АДРЕС`.
Теперь сервер должен пустить без пароля.

Если пользователю `deploy` нужен другой ключ, не тот, с которым входишь ты, отправь файл с открытым ключом на
сервер:

```
scp $env:USERPROFILE\.ssh\id_ed25519.pub АДМИН@АДРЕС:
```

и назови этот файл скрипту (на сервере, в папке `dist-deploy`):

```
sudo bash setup.sh --deploy-key ~/id_ed25519.pub
```

Так же поступи, если скрипт остановился со словами `no public key for the user deploy`: значит, у администратора
на сервере нет ни одного ключа.

### 4.4. Посмотреть, что скрипт сделает

Зайди на сервер и запусти скрипт с ключом `--dry-run`:

```
ssh АДМИН@АДРЕС
cd dist-deploy
sudo bash setup.sh --dry-run
```

Так он только печатает: каждая строка `would run: …` — команда, которую выполнит настоящий запуск. Ничего не
меняется, пароль не спрашивается. Сам пробный прогон запускает только три программы, и все три лишь спрашивают у
системы, через какие порты приходит SSH. Скрипт пишет по-английски простыми буквами, чтобы текст читался в любом
окне.

Запускай пробный прогон так же, как потом запустишь настоящий (через `sudo`, а при другом порте SSH — как в шаге
4.3): тогда строка `SSH stays open on: …` покажет те самые порты, которые откроет настоящий запуск. Найди её в
шаге `6/8` и сверь со своим портом.

### 4.5. Запустить

```
sudo bash setup.sh
```

(если ты вошёл как `root`, то просто `bash setup.sh`; при другом порте SSH — как в шаге 4.3). Скрипт идёт по шагам
и про каждый говорит, что делает:

1. ставит пакеты из репозиториев самой Ubuntu: `caddy`, `nodejs`, `ufw`, `logrotate`. По дороге он ни о чём не
   спрашивает, остальные пакеты системы не обновляет и их настройки не меняет. Ничего другого из интернета он не
   скачивает и не запускает;
2. заводит двух пользователей: `sc-trade-site` — под ним работает служба, войти им нельзя; `deploy` — для
   выкладки сайта. Пользователю `deploy` он даёт те же открытые ключи, с которыми входишь ты (шаг 4.3). Ключи,
   которые у этого пользователя уже были, остаются;
3. создаёт папки: сайт `/var/www/sc-trade.space` (пишет `deploy`, читают все), сообщения `/var/lib/sc-trade-site`
   (только служба), настройки `/etc/sc-trade-site` (пишет `root`, читает служба);
4. кладёт код службы в `/opt/sc-trade-site` (владелец `root`, служба его только читает);
5. **спрашивает пароль страницы автора** — это единственное, о чём он спросит. Дважды, и при вводе на экране
   ничего не появляется:

   ```
   The password of the admin page (16 characters or more; nothing is shown while you type):
   Once more:
   ```

   Пароль должен быть **случайным**: создай его в менеджере паролей (16 знаков или больше) и там же сохрани, а
   сюда вставь. Придуманный пароль не годится, и вот почему. Страница автора открыта всему интернету, и подбор
   пароля служба только тормозит: после пяти неверных паролей адрес ждёт 15 минут, а когда неверных много с
   разных адресов — проверяет не больше одного пароля в секунду. Остановить подбор совсем она не может: тот, у
   кого много адресов, может пробовать месяцами. Случайный пароль за это время не подобрать, а слово, дату или
   привычный пароль — можно.

   Скрипт записывает в настройки только хеш пароля; сам пароль не попадает ни в командную строку, ни в файлы, ни
   в журнал. Никуда его не вписывай и никому не пересылай — в том числе в переписку с ассистентом;
6. включает брандмауэр `ufw`: внутрь пускает SSH, 80 и 443, остальное закрыто. Порты SSH он берёт у самой системы
   (шаг 4.3) и перед включением печатает их строкой `SSH stays open on: …`. Брандмауэр он включает только после
   того, как сам `ufw` показал правило для каждого из этих портов. Если система не назвала порт или `ufw` не
   показал правило, он брандмауэр не включает, говорит об этом (и ещё раз в самом конце) и идёт дальше. Если у
   хостера в панели есть свой брандмауэр, открой там те же порты: порт SSH, 80 и 443 (443 — и TCP, и UDP);
7. запускает службу и ждёт, пока она ответит на самом сервере: `the service answers on 127.0.0.1:8787`;
8. спрашивает у Caddy, годится ли новый `Caddyfile` (`caddy validate`), и только после этого кладёт его на место.
   Если Caddy его не принял, прежний файл остаётся нетронутым, а скрипт говорит, что не так. Этот шаг последний
   не случайно: он вероятнее других остановится на сервере, которого скрипт ещё не видел. Если это случится,
   брандмауэр уже включён, а служба уже работает. В конце скрипт печатает, что проверить.

Если скрипт остановился, он пишет `STOPPED:` и причину, а следующей строкой — что этот запуск успел сделать и
чего не успел: `The server now: this run has done: …; not done: …`. Всё сделанное остаётся. Исправь причину и
запусти скрипт снова.

Повторный запуск безопасен, но это не значит, что он ничего не делает. Пользователей он заново не заводит,
пароль во второй раз не спрашивает, сообщения и настройки службы оставляет как были. Остальное он проходит
заново: свои четыре пакета обновляет, если в Ubuntu вышли новые; своим папкам выставляет тех же владельцев и те же
права; заменяет код службы тем, что лежит в папке `dist-deploy`; перезапускает службу (все открытые входы на
страницу автора при этом закрываются); заново проверяет и кладёт `Caddyfile` и велит Caddy его перечитать.

Настройки SSH-сервера скрипт не меняет. Что с ними стоит сделать — в шаге 4.11.

### 4.6. Проверка после настройки

Список идёт по порядку: от первого входа до запрета паролей. Не пропускай шаги — у каждого написано, что ты должен
увидеть. Команды с `curl.exe`, `npm` и `ssh` набираются в PowerShell на своём компьютере, остальные — на сервере.
Сертификат HTTPS Caddy получает сам, когда домен уже показывает на сервер (раздел 2); до этого адреса с `https://`
не откроются.

1. Держи открытым второе окно с входом на сервер и заранее найди в панели хостера веб-консоль сервера: она пустит
   тебя, даже если SSH перестанет пускать.
2. Порт SSH (шаг 4.3). `sudo sshd -T | grep -i '^port'` печатает `port 22`, а `echo $SSH_CONNECTION` заканчивается
   на `22`. Если хотя бы одна показала другой порт, не запускай скрипт простым `sudo`: запускай, как написано в
   шаге 4.3.
3. Система та, для которой написан скрипт. `grep -E '^(ID|VERSION_ID)=' /etc/os-release` печатает `ubuntu` и
   `"24.04"`. `apt-cache policy caddy nodejs` показывает в строках `Candidate` версии `2.6.x` и `18.19.x`.
4. Пробный прогон: `sudo bash setup.sh --dry-run` печатает восемь шагов (от `==> 1/8` до `==> 8/8`), строку
   `the site: sc-trade.space, served from /var/www/sc-trade.space; the service on 127.0.0.1:8787`, в шестом шаге —
   строку с портами SSH (в ней должен быть твой порт) и в конце `dry run: nothing is changed`.
5. Настоящий запуск: `sudo bash setup.sh`. По порядку должны появиться: `Node 18` (число может быть больше);
   `keys of deploy: N, of them new: N`; `SSH stays open on: 22`; `Status: active`, под ним строка `Default:` со
   словами `deny (incoming)` и правила `22/tcp`, `80/tcp`, `443/tcp`, `443/udp` со словом `ALLOW` (каждое дважды:
   для IPv4 и для IPv6); `the service answers on 127.0.0.1:8787`; `Valid configuration`; `Done.` Если вместо этого
   `STOPPED:` — следующая строка говорит, что сделано, а что нет (шаг 4.5).
6. Открой новое окно и войди: `ssh АДМИН@АДРЕС`. Сервер должен пустить, как раньше. Сделай это до того, как
   закроешь хоть одно окно: брандмауэр уже включён.
7. `ssh deploy@АДРЕС` пускает без пароля (первый вход спросит про отпечаток сервера — ответь `yes`). Там же:
   `id` показывает одну группу, `deploy`, а `sudo -n true` отвечает отказом. Этот пользователь не может стать
   администратором.
8. `systemctl is-active caddy sc-trade-site ufw` печатает три раза `active`.
   `sudo journalctl -u sc-trade-site -n 20 --no-pager` заканчивается строкой `started address=127.0.0.1 port=8787`,
   и в нём нет слов `226/NAMESPACE` и `218/CAPABILITIES` (если есть — шаг 4.12).
9. `sudo ss -ltnp | grep -E ':(8787|2019|80|443)\b'` показывает, что порты 8787 (служба) и 2019 (управление Caddy)
   слушают только на `127.0.0.1`, а 80 и 443 — на всех адресах.
10. Права на месте.
    `sudo stat -c '%A %U:%G %n' /etc/sc-trade-site /etc/sc-trade-site/config.json /var/lib/sc-trade-site /opt/sc-trade-site /var/www/sc-trade.space /var/log/caddy/sc-trade-error.log /etc/logrotate.d/sc-trade-site /home/deploy/.ssh/authorized_keys`
    печатает восемь строк, и начинаются они, по порядку, так: `drwxr-x--- root:sc-trade-site`;
    `-rw-r----- root:sc-trade-site`; `drwx------ sc-trade-site:sc-trade-site`; `drwxr-xr-x root:root`;
    `drwxr-xr-x deploy:deploy`; `-rw-r----- caddy:caddy`; `-rw-r--r-- root:root`; `-rw------- deploy:deploy`.
11. Пользователь выкладки не видит чужого. `sudo -u deploy cat /etc/sc-trade-site/config.json`,
    `sudo -u deploy ls /var/lib/sc-trade-site` и `sudo -u deploy touch /opt/sc-trade-site/x` — все три отвечают
    `Permission denied`.
12. Со своего компьютера. `curl.exe https://sc-trade.space/api/` отвечает `{"ok":true}`: служба работает,
    сертификат на месте. `curl.exe -i https://sc-trade.space/admin/` отвечает `303` и `Location: /admin/login`
    (без входа любой адрес под `/admin/` отправляет на страницу входа), а ещё `Cache-Control: no-store`,
    `X-Robots-Tag: noindex, nofollow`, `Content-Security-Policy`, `X-Content-Type-Options: nosniff`,
    `Strict-Transport-Security`. `curl.exe --max-time 5 http://АДРЕС:8787/api/` не получает ответа и через пять
    секунд сдаётся: снаружи служба не видна. Если первая команда пишет об ошибке сертификата — шаг 4.12, «Нет
    сертификата».
13. Выложи сайт (разделы 5 и 6). После `npm run site:deploy -- --yes` команда
    `ssh deploy@АДРЕС "ls -l /var/www/sc-trade.space"` показывает файлы с правами `-rw-r--r--` и папки с правами
    `drwxr-xr-x`, а сайт открывается в браузере.
14. Форма целиком: отправь с сайта сообщение со скриншотом и файлом лога; открой `https://sc-trade.space/admin/`,
    войди, найди сообщение, скачай вложение, удали сообщение.
15. В журнал ошибок попадает адрес, но не заголовки запроса. `sudo systemctl stop sc-trade-site`, открой в
    браузере `https://sc-trade.space/api/` (ответ будет `502`), затем `sudo systemctl start sc-trade-site`.
    Последняя запись журнала, `sudo tail -n 1 /var/log/caddy/sc-trade-error.log`: в ней есть `remote_ip` и нет
    `headers`.
16. Правило для журнала ошибок. `sudo logrotate --debug /etc/logrotate.conf 2>&1 | grep -i -A12 sc-trade-error`
    (ничего не делает, только показывает) печатает `after 1 days (28 rotations)`, и рядом нет слов `error:`,
    `duplicate` и `insecure`. Через два дня `sudo ls -ls /var/log/caddy/` показывает рядом с журналом файл
    `sc-trade-error.log.1` с владельцем `caddy`, а сам журнал небольшой. После первой ночи этого файла ещё нет:
    в первую ночь правило только запоминает журнал, переворачивает его со второй.
17. Описание службы написано верно: `systemd-analyze verify /etc/systemd/system/sc-trade-site.service` про эту
    службу ничего не печатает.
18. `sudo reboot`. Через минуту: SSH пускает, шаг 8 показывает то же самое, сайт открывается.
19. Повторный запуск: `sudo bash setup.sh` пароль не спрашивает и печатает `of them new: 0`. На странице автора те
    же сообщения, пароль прежний.
20. Только теперь — запрет входа по паролю, шаг 4.11. Новый вход там проверяется под именем администратора, а
    не `deploy`.

Чего нельзя было проверить без сервера, и что эти шаги проверяют впервые: принимает ли Caddy из Ubuntu 24.04 весь
`Caddyfile` (шаг 5) и вырезает ли он заголовки из журнала ошибок (шаг 15); как отвечают `sshd`, `ss` и `ufw` на
вопросы скрипта (шаги 2, 4 и 5); запускается ли служба со всеми ограничениями из её описания (шаги 8 и 17);
работает ли правило для журнала (шаг 16); с какими правами Windows кладёт файлы сайта на сервер (шаг 13). Если
что-то из этого не сошлось, скажи: это правится в проекте, а не руками на сервере.

### 4.7. Страница автора

`https://sc-trade.space/admin/` — вход по паролю из шага 4.5. Там список сообщений (новые сверху), поиск,
просмотр одного сообщения, скачивание вложений и удаление.

- Время везде указано по UTC.
- Поиск ищет по тексту, контакту, имени файла и дню (`2026-10-10` или `10.10.2026`). Так находится сообщение,
  которое человек попросил удалить: у него самого номера сообщения нет, он назовёт контакт, день или слова.
- Удалить можно одно сообщение (на его странице), несколько сразу (поставь галочки в списке и нажми «Удалить
  отмеченные») или всё, что нашёл поиск (ссылка «Удалить всё найденное» под списком: она ведёт на страницу,
  которая говорит, сколько сообщений будет удалено, и спрашивает ещё раз). Удалённое вернуть нельзя.
- Сообщения старше 180 дней служба удаляет сама: так обещает страница сайта «О данных».
- Место под сообщения ограничено (по умолчанию 1 ГБ). Когда занято больше 80 %, список говорит об этом первой
  строкой. Когда место кончится, форма сайта начнёт отвечать «Не получилось отправить», пока ты не удалишь лишнее.
  Чтобы место не кончилось за час, служба принимает не больше 40 МБ в сутки с одного адреса и не больше 200 МБ в
  час от всех вместе; сверх этого форма отвечает «Слишком много сообщений подряд». Все пределы — в
  `/etc/sc-trade-site/config.json` (образец: `dist-deploy/server/config.example.json`).
- Вход держится 12 часов. После пяти неверных паролей с одного адреса вход с него закрыт на 15 минут. Счёт идёт
  по адресу, а не по человеку: если адрес в интернете у тебя общий с кем-то (один роутер, сеть оператора, VPN),
  этот кто-то пятью неверными паролями закроет вход на 15 минут и тебе. Подожди или зайди с другого адреса.
- После перезапуска службы надо войти заново: входы хранятся только в её памяти.

### 4.8. Обновить службу

Собери папку заново (шаг 4.1), убери старую на сервере и отправь новую (шаг 4.2), запусти `sudo bash setup.sh`
ещё раз. Пароль он не спросит (настройки уже есть), код службы заменит и службу перезапустит. Сообщения остаются
на месте.

То же самое — если изменился `Caddyfile` (например, включена аналитика): его кладёт на сервер тот же скрипт.

### 4.9. Сменить пароль

На сервере, в папке `dist-deploy`:

```
sudo bash setup.sh --reset-password
```

Скрипт спросит новый пароль так же, как в первый раз, запишет его хеш и перезапустит службу. Больше он при этом
ничего не делает: пакеты, пользователей, брандмауэр и Caddy не трогает. Все открытые входы на страницу автора
закрываются.

### 4.10. Где лежат данные и как сделать копию

- Сообщения — `/var/lib/sc-trade-site`: в `messages` по файлу JSON на сообщение, в `files` — папка с его
  вложениями. Читать эту папку может только служба (и `root`). Адреса отправителя в этих файлах нет.
  Файл `sc-trade-site.marker` там же — метка службы: в непустой папке без этой метки служба не запустится и
  ничего в ней не тронет (так она не примет за свою чужую папку, вписанную в настройки по ошибке). Не удаляй его.
- Настройки службы — `/etc/sc-trade-site/config.json`: домен, порт, папка данных, хеш пароля и пределы. Образец —
  `dist-deploy/server/config.example.json`. Копия этому файлу не нужна: скрипт создаст его заново.
- Журнал службы — `journalctl -u sc-trade-site`. В нём время, итог и размеры; текста сообщений, контактов и
  адресов там нет.
- Журнал ошибок веб-сервера — `/var/log/caddy/sc-trade-error.log`, хранится не дольше 30 дней. Журнала посещений
  нет.

Копия сообщений, на сервере, в домашней папке администратора:

```
cd ~
sudo sh -c 'umask 077; tar -czf sc-trade-messages.tar.gz -C /var/lib sc-trade-site'
sudo chown "$USER" sc-trade-messages.tar.gz
```

`umask 077` закрывает архив от остальных пользователей сервера: в нём то, что прислали люди. Вторая команда отдаёт
его тебе, чтобы ты мог его забрать.

Забрать копию на свой компьютер и убрать с сервера:

```
scp АДМИН@АДРЕС:sc-trade-messages.tar.gz .
ssh АДМИН@АДРЕС "rm sc-trade-messages.tar.gz"
```

Обещание «хранится до 180 дней, либо удаляется раньше по просьбе» относится и к копии: не держи копии дольше, а
если человек попросил удалить сообщение — удали его и из копий. То же касается снимков и резервных копий всего
сервера, которые делает хостер: если они включены, посмотри в его панели, сколько они хранятся.

Вернуть сообщения из копии (на сервере, в папке, где лежит архив):

```
sudo systemctl stop sc-trade-site
sudo tar -xzf sc-trade-messages.tar.gz -C /var/lib
sudo chown -R sc-trade-site:sc-trade-site /var/lib/sc-trade-site
sudo systemctl start sc-trade-site
```

### 4.11. SSH: запретить вход по паролю

Скрипт настройки SSH-сервера не трогает: ошибка в них закрыла бы тебе вход на собственный сервер. Запретить вход
по паролю стоит, но только когда проверен твой собственный вход по ключу. Если запретить пароли, а ключа
администратора на сервере нет, тебя не пустит ничто, кроме веб-консоли хостера.

Важно, чей вход проверять. Вход пользователем `deploy` не считается: он показывает только то, что работает ключ
пользователя выкладки, а починить сервер этот пользователь не может. Проверять надо вход **администратора** —
того, под кем ты настраивал сервер.

1. Убедись, что ключ администратора лежит на сервере. Если хостер принял ключ, когда ты создавал сервер, или ты
   положил его в шаге 4.3, он уже там. Если нет, положи сейчас. На своём компьютере, в PowerShell, одной строкой
   (команда спросит пароль администратора):

   ```
   Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | ssh АДМИН@АДРЕС "mkdir -p ~/.ssh && chmod 700 ~/.ssh && tr -d '\r' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
   ```

2. Открой **новое окно** PowerShell и войди администратором:

   ```
   ssh АДМИН@АДРЕС
   ```

   Сервер не должен спросить пароль. Если спросил — остановись: ключ администратора не работает, и запрет паролей
   закроет тебе вход. Вернись к первому шагу.

   Ту же проверку можно сделать одной командой. Она должна напечатать число не меньше 1 и тоже ничего не спросить:

   ```
   ssh АДМИН@АДРЕС "grep -c . ~/.ssh/authorized_keys"
   ```

3. Дальше работай, **не закрывая окно**, в котором ты уже на сервере: оно понадобится, если что-то пойдёт не так.
   Создай файл настроек одной командой, на сервере:

   ```
   printf '%s\n' 'PasswordAuthentication no' 'KbdInteractiveAuthentication no' 'PermitRootLogin prohibit-password' | sudo tee /etc/ssh/sshd_config.d/00-sc-trade.conf
   ```

   Команда повторит эти три строки на экране — так и должно быть. Имя файла начинается с `00`, чтобы он читался
   раньше остальных: SSH-сервер берёт первое значение, которое встретил.

4. Проверь, что в настройках нет ошибки. Команда должна ничего не напечатать:

   ```
   sudo sshd -t
   ```

5. Примени:

   ```
   sudo systemctl reload ssh
   ```

6. Ещё раз открой новое окно и войди администратором:

   ```
   ssh АДМИН@АДРЕС
   ```

   Пустил без пароля — готово. Не пустил — в окне, которое ты не закрывал, верни всё назад и разберись, почему
   ключ не подошёл:

   ```
   sudo rm /etc/ssh/sshd_config.d/00-sc-trade.conf
   sudo systemctl reload ssh
   ```

Вход через веб-консоль хостера этот запрет не затрагивает: он идёт не через SSH.

### 4.12. Если что-то не работает

- Скрипт написал `the firewall is NOT touched` или `the firewall is NOT turned on`. В первом случае система не
  назвала ему порт SSH, во втором `ufw` не показал правило для этого порта. Брандмауэр он включать не стал, чтобы
  не закрыть тебе вход; всё остальное он сделал. Посмотри порт сам и запусти скрипт ещё раз так, как написано в
  шаге 4.3. Пока брандмауэр не включён, сервер открыт так же, как был до запуска.

- Скрипт написал `the service does not answer on 127.0.0.1:8787`. Служба не запустилась или не отвечает: смотри
  следующие два пункта.

- Служба не стартует:

  ```
  systemctl status sc-trade-site
  journalctl -u sc-trade-site -n 50
  ```

  Если дело в настройках, служба пишет, чего не хватает, по имени: `sc-trade-site does not start: …
  "dataDir" is missing`. Поправь `/etc/sc-trade-site/config.json` и перезапусти: `sudo systemctl restart
  sc-trade-site`. После нескольких неудачных запусков подряд systemd перестаёт пробовать; тогда сначала
  `sudo systemctl reset-failed sc-trade-site`.

- Служба не стартует, а в журнале вместо её слов — слова systemd (`Failed to set up mount namespacing`,
  `status=226/NAMESPACE`, `status=218/CAPABILITIES` и похожие). Значит, ей мешает одно из ограничений в файле
  `/etc/systemd/system/sc-trade-site.service`: этот файл тоже никто до тебя не запускал. Поставь `#` перед строкой,
  которую называет журнал, затем `sudo systemctl daemon-reload` и `sudo systemctl restart sc-trade-site`. И скажи
  об этом: файл в проекте надо поправить.

- Нет сертификата: браузер или `curl.exe` пишут об ошибке сертификата, а сайт по `https://` не открывается. Свои
  сообщения Caddy пишет в журнал ошибок, а не в `journalctl`; посмотри, что он говорит о сертификате:

  ```
  sudo tail -n 20 /var/log/caddy/sc-trade-error.log
  ```

  Чаще всего домен ещё не показывает на сервер. Проверь: в ответе должен быть адрес сервера (раздел 2).

  ```
  nslookup sc-trade.space
  ```

  Если у хостера в панели есть свой брандмауэр, открой в нём порты 80 и 443. Когда причина исправлена, вели Caddy
  попробовать снова (сам он тоже пробует, но с растущими паузами):

  ```
  sudo systemctl reload caddy
  ```

- Форма на сайте отвечает «Не получилось отправить». Проверь `curl.exe https://sc-trade.space/api/`: если там не
  `{"ok":true}`, служба не работает (см. выше) или Caddy до неё не достаёт:

  ```
  journalctl -u caddy -n 50
  sudo tail -n 20 /var/log/caddy/sc-trade-error.log
  ```

- Форма отвечает «Сообщение не принято: оно похоже на автоматическое» на обычное сообщение. Посмотри журнал
  службы: строка `feedback spam … why=origin` значит, что в настройках службы записан не тот домен, с которого
  открыт сайт.

- Caddy не принял `Caddyfile`. Скрипт оставил прежний и показал, что сказал Caddy. Проверить файл руками
  (именно через `sudo` и только после того, как скрипт хотя бы раз дошёл до шага 3: он создаёт файл журнала с
  нужным владельцем):

  ```
  sudo caddy validate --config ~/dist-deploy/Caddyfile --adapter caddyfile
  ```

## 5. Куда выкладывать: `site/deploy.local.json`

Скопируй `site/deploy.example.json` в `site/deploy.local.json` и впиши своё:

```json
{
  "host": "203.0.113.7",
  "user": "deploy",
  "path": "/var/www/sc-trade.space",
  "port": 22
}
```

- `host` — имя сервера или его адрес IPv4 (адрес IPv6 сюда не подходит: выкладка его не примет);
- `user` — пользователь на сервере, которому можно писать в папку сайта;
- `path` — папка сайта на сервере (по умолчанию `/var/www/sc-trade.space`);
- `port` — порт SSH (по умолчанию 22).

Пароля и ключа в этом файле нет и быть не должно: если вписать, выкладка откажется работать. Файл остаётся только
на твоём компьютере, в репозиторий он не попадает.

## 6. Собрать и выложить

1. Собери установщик программы: `npm run tauri build`.
   Он появится в `src-tauri\target\release\bundle\nsis\`.

2. Собери сайт с этим установщиком (вместо `<версия>` — номер версии, как в имени файла из первого шага):

   ```
   npm run site:build -- --installer "src-tauri\target\release\bundle\nsis\SC Trade_<версия>_x64-setup.exe"
   ```

   Получится `site/dist` (сам сайт: его отправляет выкладка) и рядом `site/dist-deploy` (папка для настройки
   сервера из раздела 4; выкладка её не трогает). Сборка сама считает размер и SHA-256 установщика и остановится,
   если версия в имени файла не та, что в `package.json`.

3. Посмотри, что получилось (не обязательно): `npm run site:check` снимает страницы в браузере и кладёт картинки
   в `.superpowers/site-check/`. Или просто открой `site\dist\index.html` двойным кликом.

4. Сухой прогон: печатает, что и куда уйдёт, и ничего не отправляет.

   ```
   npm run site:deploy
   ```

5. Выкладка:

   ```
   npm run site:deploy -- --yes
   ```

Выкладка только создаёт папки и кладёт файлы. Она ничего не удаляет на сервере и ничего на нём не настраивает.
Сайт, собранный без установщика (`--no-installer`, для просмотра), она выкладывать откажется.

## 7. Проверить после выкладки

- Открой `https://sc-trade.space/` и `https://sc-trade.space/en/`: страницы на месте, в адресной строке замок.
- `http://sc-trade.space/` должен сам перейти на `https://`.
- Скачай установщик кнопкой и сверь сумму с той, что на странице (вместо `<версия>` — номер скачанной версии):

  ```
  Get-FileHash .\SC-Trade-<версия>-setup.exe
  ```

- Заголовки страницы:

  ```
  curl.exe -I https://sc-trade.space/
  ```

  В ответе должны быть `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`,
  `X-Frame-Options: DENY`, `Strict-Transport-Security`.

- Установщик отдаётся как скачивание:

  ```
  curl.exe -I https://sc-trade.space/download/SC-Trade-<версия>-setup.exe
  ```

  В ответе должно быть `Content-Disposition: attachment`.

- Несуществующий адрес отвечает своей страницей и кодом 404:

  ```
  curl.exe -I https://sc-trade.space/net-takoy-stranicy
  ```

- Форма обратной связи: отправь сообщение со скриншотом и файлом лога и найди его на странице автора
  (`https://sc-trade.space/admin/`, шаги 4.6 и 4.7). Пока служба на сервере не запущена, форма честно отвечает
  «Не получилось отправить».

## 8. Обновить версию

1. Подними версию программы (она записана в `package.json`, `src-tauri/tauri.conf.json` и `src-tauri/Cargo.toml`)
   и собери новый установщик.
2. Собери сайт с новым установщиком (раздел 6, шаг 2) и выложи (шаги 4 и 5).

На странице всегда только последняя версия. Старые установщики при этом остаются лежать на сервере в папке
`download` (выкладка ничего не удаляет) и доступны по прямой ссылке. Убрать лишний можно руками (вместо
`<старая версия>` — номер той версии, которую убираешь):

```
ssh deploy@АДРЕС "ls /var/www/sc-trade.space/download"
ssh deploy@АДРЕС "rm /var/www/sc-trade.space/download/SC-Trade-<старая версия>-setup.exe"
```

## 9. Что нужно знать про настройки сайта

Все настройки — в `site/site.config.json`: автор, год, домен, ссылки, адрес формы, идентификатор аналитики.
Тексты страниц — в `site/i18n/ru.json` и `site/i18n/en.json`.

- Аналитика выключена, пока `analytics.ga4Id` пуст: на сайте нет ни баннера, ни чего-либо от Google. Если вписать
  идентификатор (вида `G-XXXXXXXXXX`) и собрать сайт заново, появится баннер согласия, а скрипт Google будет
  загружаться только после нажатия «Разрешить». При этом меняется и `site/dist-deploy/Caddyfile` (в нём список
  адресов, к которым страницам разрешено обращаться): его надо заново положить на сервер (шаг 4.8), иначе
  браузеры не пустят аналитику.
- Фоновый ролик первого экрана: `site/VIDEO.md`.
- Готовый `Caddyfile` на этом компьютере не проверялся самим Caddy (его здесь нет). На сервере его проверяет
  скрипт настройки (`caddy validate`), и только после этого кладёт на место.
- Адрес и порт службы обратной связи (`server.service`) и домен записаны и в `Caddyfile`, и в настройках службы на
  сервере. Если поменять их в `site/site.config.json`, скрипт настройки при следующем запуске скажет, что
  настройки на сервере (`/etc/sc-trade-site/config.json`) им не соответствуют: поправь там `domain` и `port`.

## 10. Что отложено

- **Почта.** Служба никуда ничего не отправляет: ни писем, ни сообщений в мессенджеры. Новые обращения видны
  только на странице автора — заглядывай туда сам. Уведомления появятся позже; тогда изменится и страница сайта
  «О данных», где сейчас сказано, что обращения видит только автор.
- **Аналитика.** Выключена, пока `analytics.ga4Id` в `site/site.config.json` пуст (раздел 9).
